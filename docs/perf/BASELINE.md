# FARWAKE performance baseline

**Commit:** `37745f19670be8c82b560b5cf9af2672d27b3ac7` (`37745f1` on `farwake/integration`)
**Measured:** 11 Nov 2026, headless Google Chrome 157.0.8103.50 via Playwright-core 1.65.0
**Harness:** `node perf/run-headless.mjs` on `http://127.0.0.1:47321` with a fresh browser profile per measurement

> **These are not iPhone frame times.** The runner emulates an iPhone 14 screen (390×844 CSS px, devicePixelRatio 3, iPhone Safari user agent, touch) and asks Chromium for a **4× CPU throttle**. That is Blink/V8 with software raster. It is not iPhone Safari (WebKit/JavaScriptCore, Metal-backed canvas, ProMotion or Low Power Mode). GPU fill, compositing, and `backdrop-filter` are invisible here. Use the numbers to compare scenes, and later to compare an optimisation against this commit. Do not quote them as phone milliseconds.

Frame time is the JavaScript duration of the `requestAnimationFrame` callback (simulation, presentation, draw, and the 0.8 s UI refresh when it lands). It does not include GPU time. Percentiles use linear interpolation on the sorted sample. A long frame is a callback longer than 16.7 ms or 33.3 ms. Allocation is Chromium's sampling heap profiler (32,768-byte interval, including objects collected by minor and major GC); KB/frame is `sampleCount × interval / frames / 1024`. The sampler runs during the window, so it adds some overhead of its own. `performance.memory` was available. The used-heap delta across a window is not the allocation rate: GC runs during the sample, and the late-colony windows ended several MB below where they started.

Playwright 1.65's built-in iPhone 14 viewport is 390×664 because it subtracts Safari toolbars. The runner pins **390×844**, which is the full screen this baseline and the render audit measure. The game's own header and nav then leave a **390×712** CSS canvas.

Each window is 5 s of recording after 1.5 s of warmup, so the first-sight terrain bake is not in the steady-state sample. Raw JSON for this run is regenerated by the command above into `perf/results/` (git-ignored).

Median of the three medians: Day 2 **1.7 ms**, late colony **11.7 ms**, idle **1.5 ms**.

Every one of those runs used the same canvas: **390×712 CSS**, backing store **780×1424**, `devicePixelRatio` **3**. Balanced preset caps the backing store at 2×, so a DPR 3 screen is upscaled by the compositor. Callback intervals were about 22–23 ms on Day 2 and idle (the compositor was not locked at 30 Hz under this throttle) and about 49–54 ms on the late colony, where the callback itself was most of the frame.

The Day 2 clock is set on the fresh expedition. Day 1 is not simulated. `tick()` reads `performance.now()`, so a fast-forward would not be reproducible. Colonist energy, hunger, and positions are pinned for the same reason. The late colony is a stress layout, not a played save: 49 finished structures (2 dormitory, 2 warehouse, 5 shelter, 3 cabin, 7 garden, 2 greenhouse, 2 workshop, 2 smelter, 2 kitchen, 2 shed, 2 clinic, 6 solar, 4 wind, 8 lamppost) plus 36 paths and 36 roads, history counters set, fog revealed within 18 tiles of the landing, and 20 cloned colonists. It did **not** produce the multi-second stalls the render audit saw on a different synthetic layout. It did produce one frame of about **155–161 ms** in every 5 s window.

On this small colony the simulation adds little frame JS (1.7 ms vs 1.5 ms paused) and roughly doubles allocation (about 53 KB/frame vs 30). On the late colony the simulation dominates allocation (about 800 KB/frame vs 168 KB/frame paused at the same zoom) and pushes p95 from about 10 ms to about 21 ms.

## Proposals (not implemented)

Nothing in this branch changes the renderer, the camera, input, or the UI. The ranked list from the render audit is the proposal set. Each one still needs its owner's file and a before/after on this harness. Full file and line references are in `docs/perf/RENDER_AUDIT.md` §6.

1. **Cached fog layer.** One `drawImage` instead of a `fillRect` per fogged tile. Largest draw-call cut at zoom 0.6, and it removes the fog grid seams. Measure fillRect/frame and frame-JS median on `fresh-z06` and `day2`.
2. **Zero-allocation draw path.** Keep sorted building and colonist lists, and stop rebuilding plate keys every frame. Target the ~170 KB/frame render allocation on `grown-day` / `grown-night`.
3. **Bound simulation work per frame.** An occupancy grid for `buildingAt`, reused path buffers, and staggered idle `getTarget` retries. This is the late-colony gap (about 800 KB/frame and a 155 ms spike). It can change pathing and task choice, so it needs a determinism check from Systems and QA. Do not treat the 155 ms spike as the multi-second stalls from the audit; those still need a real long-run save.
4. **Snap the camera translation to device pixels**, and colonist draw origins to whole world pixels. Visual, not a frame-time win.
5. **Snap zoom easing to the target, and fix the confirmed pinch bugs** (finger swap, missing drag for the surviving finger, no camera clamp while pinching, the 7 px drag lag). Gesture feel, owned with UI & Mobile.
6. **Cache night-light and sky gradients** the way glow halos are already cached. Compare `grown-night` gradient counts and, on a phone, night rain.
7. **Bake terrain chunks off the first frame that sees them.** The harness warmup currently hides the 30–40 ms first-sight hitch; a scripted pan across an unseen map is the measurement.
8. **Lighten the Performance preset** so presentation runs at the draw cadence, and consider a 1.5× backing store instead of 1×. `grown-performance` already shows the bimodal skip and the soft 1× backing store.
9. **Try `image-rendering: pixelated` on `#world`.** A visual trial. The 1.5× upscale from a 2× backing store on a DPR 3 screen will not be even pixels. Kyle has to judge it on the phone.
10. **Pixel-perfect mode** (native DPR backing store and integer device-scale zoom stops) only after the cheap cuts. It draws about 2.25× more pixels per full-screen fill.
11. **Diff the HUD instead of rewriting `innerHTML` every 0.8 s.** Small in Chromium; may matter under `backdrop-filter` in WebKit.
12. **`backdrop-filter` trial** with the inspector card open. iPhone-only. This harness cannot see it.

Also proposed, and **not done**, because it edits game files this branch does not own: Version B from the audit, a few lines in `src/game.html` (and therefore a rebuilt `index.html`) that load the recorder when `?perf=1` and time `tick`, `advanceWorld`, and `draw` separately. The external harness can only time the whole callback. Phase splits are the reason to ask ChatGPT Work for that hook later. A main-canvas-only op counter has the same limit; the external counter covers every 2D context.

No real Day 50 / Day 100 save was available. `perf/fixtures/README.md` is where one goes. The `fixture` scene loads it through the game's own `load()` validator.

## What this baseline cannot answer

- iPhone Safari frame time, GPU cost, `backdrop-filter`, thermal throttling, battery, JavaScriptCore GC, or Low Power Mode.
- Whether a real long-running colony hits the multi-second simulation stalls from the audit. This synthetic colony did not.
- WebKit's canvas-memory ceiling on iPhone 14.
